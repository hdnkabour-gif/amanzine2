# تشريح AMANZINE — الخريطة الشاملة

> **الغرض:** أن تفهم المشروع بالكامل كأنّك تعرف بيتك — كل ملفّ، كل علاقة، وكيف
> تنتقل المعلومة من لحظة كتابة المستخدم حتى ظهور النتيجة. وثيقة **فهم** لا ميزة.
> كل الأرقام والشجرة مستخرَجة من الكود نفسه (لحظة كتابة هذه الوثيقة).

---

## ١. الهويّة والتموضع — ما هو AMANZINE؟

**AMANZINE = نظام تشغيل للحاجة (Need OS).** ليس متجرًا ولا سوق إعلانات ولا تطبيق
توصيل. الفكرة الجوهريّة: **المستخدم يقول حاجته بالدارجة، والعقل يفهمها ويوصّله للحلّ.**

السلسلة الحاكمة: `حاجة → إدراك (understand) → قرار → إجراء → ذاكرة`.

### ما الذي يميّزه؟ (بصدق)

| المنصّة | كيف تعمل | الفرق الجوهريّ مع AMANZINE |
|---|---|---|
| **Avito · Ouedkniss · Facebook Marketplace** | إعلانات مبوّبة: تتصفّح فئات وتبحث بكلمة، ويجب أن تعرف **ماذا** تريد ومن. | AMANZINE يبدأ من **الحاجة بلغتك** («الما كيهرب») لا من فئة، فيستنتج المهنة والحلّ. |
| **Jumia · Glovo** | كتالوج/توصيل جاهز لأصناف محدّدة. | AMANZINE ليس كتالوجًا؛ يفهم **أيّ حاجة في أيّ مجال** من الكلام. |
| **Google** | يعيد روابط تبحث فيها بنفسك. | AMANZINE يعيد **حلًّا محسومًا** (مهنة + مزوّد + إجراء) في سياق مغربيّ (دارجة + مدن). |

**الخلاصة:** الآخرون = «تصفّح → جد». AMANZINE = «قُل حاجتك → نفهمك → نلقّي الحلّ».
هذا هو التمايز، وهو مدعوم بالمعمار لا بالشعار.

## ٢. تدفّق المعلومة الكامل — من الكتابة إلى النتيجة

الرحلة الحقيقيّة (بأسماء الملفّات والدوالّ):

```
المستخدم يكتب: «الما كيهرب فالدار البيضاء بزربة»
  │
  ▼  src/pages/LivingHome.tsx        (الصفحة الرئيسيّة: «شنو محتاج؟»)
  │
  ▼  src/lib/core/orchestrator.ts → orchestrate(raw, ctx)   (القلب — يقرّر المسار)
  │      ├─ parseNeed()  ……… src/lib/needEngine.ts   (النيّة + الرحلة: طلب/عرض)
  │      └─ resolvePlugin() ……… أيّ مجال (Plugin/Journey)
  │
  ▼  src/lib/akg/kb/index.ts → understand(text)     (نقطة الإدراك الوحيدة — القانون #5)
  │      1) findProblemBySymptom()  ……… symptomGraph.ts   «الما كيهرب» ⇒ عطل «تسرّب ماء»
  │      2) problem.solutions[0]    ……… problems.ts       العطل ⇒ مهنة «سبّاك» + قدرات
  │      3) matchApprovedMemory()   ……… kb/memory.ts      معرفة معتمَدة بشريًّا (إن وُجدت)
  │      4) cityInText()            ……… geo.ts            «الدار البيضاء»
  │      5) context(urgent/night/…) ……… كلمات السياق      «بزربة» ⇒ مستعجل
  │      ⇒ Understanding { problem, profession, city, confidence, reasoning[], learned }
  │
  ▼  القرار/العرض:
  │      ├─ src/components/UnderstandingCard.tsx   «فهمنا طلبك» + زرّ الحلّ
  │      └─ src/lib/inference.ts → kbInfer()       (يستهلك understand للبحث/النتائج)
  │
  ▼  الذاكرة:  src/lib/experienceLog.ts → logInteraction()   (تُسجَّل القصّة كاملة)
  │      └─ src/services/api.ts → trackAPI/searchAPI   (توحيد مع الخادم)
  │
  ▼  الخادم:  server/routes/*  (auth · products · orders · listings · ai · knowledge) + PostgreSQL
```

**نقاط القرار الثلاث:**
1. **طلب أم عرض؟** يُقرَّر في `parseNeed()` من **النيّة** لا من الحساب (تفصيل §٣).
2. **أيّ مهنة؟** من `understand()`: عرَض → عطل → `solutions[0].profession`.
3. **أيّ مدينة؟** من `cityInText()` (سجلّ الجغرافيا، ٤٨ مدينة).

## ٣. العقل — كيف يميّز ويقرّر

### كيف يعرف: طلب / عرض / خدمة / مجرّد سؤال؟
كلّه في `src/lib/needEngine.ts` (الدالّة `parseNeed`)، بالكلمات لا بالدور:

| الحالة | كيف يُكتشَف | النيّة (Intent) | الوجهة |
|---|---|---|---|
| **يطلب مهنيًّا** | «بغيت سبّاك» · «فين نلقى» | `find_pro` / `urgent` | نتائج مهنيّين |
| **يريد الشراء** | «نشري» · «نقلب على» · «بغيت نشري» | `buy` | السوق/نتائج |
| **يريد البيع** | «بغيت نبيع» · «للبيع» · «عندي…» | `sell` | صفحة النشر |
| **يقدّم خدمة** | زرّ «أضف خدمة» / نصّ الخدمة | `create_service` | صفحة النشر |
| **يفتح متجرًا** | «افتح متجر» | `create_store` | لوحة التاجر |
| **مجرّد سؤال/تصفّح** | لا مطابقة قويّة | `unknown` → اكتشف | العقل الحيّ يسجّله كـ«لم يُفهَم» |

> ملاحظة مهمّة (وثغرة قبل البيتا): **العرض/الطلب مبنيّ بالنيّة، وهذا صحيح.** لكن
> **التسجيل** الحاليّ يجعل كلّ مسجّل `role:'admin'` (يفترض تاجرًا). التوصية: تسجيل
> بسيط + بطاقات «شنو بغيتي تدير؟» (حساب واحد، قدرات متعدّدة).

### الاستدلال قابل للتفسير
كلّ قرار يخرج معه `reasoning[]` — لماذا هذا العطل، هذه المهنة، هذه الثقة. تراه في
بطاقة «فهمنا طلبك»، وفي مركز القيادة › العقل الحيّ، ودليل المالك.

**فجوات المعرفة الحاليّة:**
- **مهنتان بلا أعراض:** `diagnostic` (تشخيص شامل — عرضيّ) و`tire_tech` (**مكرّرة** مع `tire_technician`).
- **قدرات فارغة** في المهن الجديدة (صبّاغ/بنّاي/حلّاق…): تُفهَم لكن بلا قدرات مفصّلة بعد.
- **قدرة يتيمة:** `install_heater` (لا عطل يطلبها).
- **المفردات ٢١ فقط** — قليلة لغِنى الدارجة.

## ٦. نقاط القوّة والضعف

**قوّة:**
- عقل يفهم الدارجة من العرَض لا من اسم المهنة (٦٩ نمطًا)، **مختبَر** (`npm test`).
- بنية مربوطة: `0` روابط مكسورة، `0` خدمات يتيمة.
- كل كيان **يفسّر نفسه** (`describe`) + التطبيق يعرف نفسه (`systemMap` + دليل المالك).
- حلقة تعلّم بشريّة مغلقة (Observe→Suggest→Approve→**Apply**).

**ضعف (قبل البيتا):**
- المعرفة **بذرة** (قدرات فارغة لبعض المهن، مفردات قليلة، مهنتان بلا مسار).
- **التسجيل** يفترض تاجرًا (لا أدوار/نيّات عند الدخول).
- **بيانات العمل فارغة** (لا مزوّدون/طلبات حقيقيّون — البيتا تملؤها).
- أوّل تجربة: splash بطيء (يُراجَع لاحقًا بالبيانات، لا الآن).

## ٧. خطّة العمل (المتّفق عليها)

1. **فهم النظام** ← هذه الوثيقة + دليل المالك داخل التطبيق.
2. **تنظيف وتحسين** ← توحيد التكرار · تحسين التسجيل · إكمال المعرفة · Landing/Tour/Splash.
3. **Knowledge Studio** ← إدخال المعرفة بوثيقة (فهم → مقارنة → شرح → معاينة الأثر → موافقة → نشر). يُبنى **بعد** الفهم لأنه أداة إدارة هذا النظام.
4. **البيتا المغلقة** ← أوّل مزوّد/تاجر/زبون (`docs/BETA_SPRINT.md`).

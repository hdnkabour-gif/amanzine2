# 06 — قواعد التطوير (Development Rules)

> كيف نطوّر AMANZINE **دون خرق الدستور**؟ هذه قواعد عملية للـ commit اليومي.
> تنفيذ للدستور (`01`)، لا بديل عنه. عند التعارض، `01` هو الحكم.

---

## القاعدة الذهبية

قبل أي تغيير، اسأل — بهذا الترتيب:

1. **هل يقرّب AMANZINE من رؤيته أم يبعده؟** (القانون ٨) — إن أبعد، توقّف.
2. **هل يبدأ من نيّة المستخدم أم من فئة؟** (القانون ١)
3. **هل يمكن إنجازه بتوسيع موجود بدل إضافة جديد؟** (القانون ٤)
4. **هل يكسر عقدًا؟** (القانون ٩) — إن كسر، فهو `v2` + Decision Record.

---

## التطوّر لا الهدم (Evolution, not Rewrite)

**النموذج المعماري المستهدف** (المعتمَد في `DR-0001`):

```
Intent → Knowledge → Decision → Execution → Presentation
```

لكن الوصول إليه يكون **بالتطوّر التدريجي فوق الكود القائم**، لا بإعادة هيكلة كبرى دفعة واحدة:

- ❌ **ممنوع**: إنشاء عشرات المجلّدات/الملفّات الفارغة (`core/ intent/ decision/ execution/ …`) قبل وجود منطق حقيقي يسكنها. هذا دَينٌ لا ميزة.
- ✅ **مطلوب**: كل طبقة تُستخرَج من الكود الحالي **حين ينضج منطقها فعلًا**، خلف نفس العقد.
- مثال: طبقة `Decision` تعيش اليوم داخل `search.js`؛ تُفصَل إلى ملفّها **حين** تتجاوز قواعدها بضعة أسطر — لا قبل.

> القاعدة: لا يُنشأ ملف/مجلّد إلا ومعه منطق يبرّر وجوده اليوم. الهيكل يتبع الكود، لا العكس.

---

## حدود المسؤولية (Layer Boundaries)

| الطبقة | تفعل | لا تفعل |
|-------|------|---------|
| **Intent** | تحوّل النص إلى `intent/v1` | لا تقرّر المحرّك، لا تبحث |
| **Knowledge** | تعرف المرادفات/العلاقات/الفئات | لا تبحث، لا تعرض |
| **Decision** | تختار المحرّك من النيّة | لا تنفّذ الاستعلام |
| **Execution/Search** | تنفّذ على المحرّك المختار | **لا تقرّر** (القانون ٣) |
| **Presentation** | ترتّب العرض حسب القدرات | لا تحتوي منطق أعمال |

كسر هذه الحدود (مثلًا: `Search` يقرّر المحرّك) = مخالفة تُرفَض في المراجعة.

---

## قواعد الكود

1. **لا كتابة مباشرة للقاموس** من أي مصدر — المسار: اقتراح → AI → مراجعة → نشر (القانون ٥).
2. **AI يفسّر لا يجيب** — أي كود يجعل AI يخترع بيانات أو يحادث عامًّا = مرفوض (القانون ٢).
3. **العقود ثابتة ومنسوخة الإصدار** — إضافة حقل غير كاسر تبقى ضمن نفس الإصدار؛ حذف/تغيير دلالة ⇒ إصدار جديد + DR.
4. **القدرات لا الأنواع** — لا `if (type === 'store')` في الواجهة؛ تحقّق من القدرة.
5. **Facade لا Store** — لا جدول موحّد جديد دون DR؛ الأنواع الجديدة = Adapter.
6. **أمان أولًا** — لا endpoint يسمح للمستخدم برفع رصيده/تخطّي العزل؛ كل مسار عام يكشف المنشور/المعتمَد فقط ومحدود المعدّل.

## قبل كل commit (Checklist)

- [ ] لا يخالف بندًا في `01_CONSTITUTION` (وإلا: DR أولًا).
- [ ] `tsc` نظيف + `npm run build` ينجح.
- [ ] `cd server && npm test` أخضر (لا تراجع).
- [ ] لم أُنشئ ملفّات هيكلية فارغة.
- [ ] العقود لم تُكسَر (أو رُفع الإصدار + DR).
- [ ] رسالة commit وصفية (Conventional Commits).

---

## متى يلزم Decision Record؟

يلزم DR (في `docs/decisions/`) لأيّ من:

- محرّك جديد · طبقة جديدة · جدول موحّد جديد.
- كسر عقد (رفع إصدار).
- تغيير في الرؤية أو حدود الطبقات.
- إعادة هيكلة تتجاوز ملفًّا واحدًا.

**لا يلزم DR** لـ: إصلاح خطأ، توسيع غير كاسر لعقد، تحسين أداء داخلي، إضافة اختبار، تعديل واجهة ضمن نفس الفلسفة.

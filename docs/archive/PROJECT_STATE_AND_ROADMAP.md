## 6. ما نحتاجه لإضافة الـ Marketplace + الميزات المتبقية

**تحوّل معماري (تفاصيله في `MARKETPLACE_ANALYSIS.md`):**
1. **أدوار حقيقية:** `users.role: admin|store|seller|customer` + تشديد العزل (اليوم على مستوى routes).
2. **كيان `listings`** (منتج/خدمة) بحالة `pending→approved→rejected→suspended` + `vendor_id` + `city`.
3. **البائع السريع:** سجل vendor خفيف من الهاتف + **OTP (موجود!)** بلا حساب.
4. **كتالوج عام موحّد** (اليوم لكل متجر منفصل) يجمع `approved` عبر كل البائعين.
5. **طابور موافقة الأدمن** + توجيه الطلب **مباشرة للبائع** (إشعار WhatsApp موجود).
6. **مونتزة:** ترويج/اشتراك أولاً (يعمل مع COD)، عمولة لاحقاً مع CMI.
7. جداول: `reviews, reports, subscriptions, promotions, messages` (+ `commissions/payouts` لاحقاً).

**يُعاد استخدامه مباشرة:** نموذج المنتج/الخدمة، Cloudinary، السلة، `orders/public`، إشعار WhatsApp، OTP، WS.

## 7. خارطة الطريق المقترحة (بالترتيب)

**المسار أ — تصليب الإنتاج (قبل أي ميزة كبيرة):**
1. Backup حقيقي (Supabase/S3) + ربط Sentry (DSN).
2. خفض ديون الأنواع تدريجياً (نوع `Settings`/`AppSettings` كامل) + اختبارات Frontend.

**المسار ب — الـ Marketplace (MVP مركّز):**
3. خدمات + **مدينة واحدة**: البائع السريع (OTP) → listing `pending` → طابور موافقة الأدمن.
4. كتالوج خدمات موحّد → طلب يصل البائع مباشرة (الأدمن يراقب فقط).
5. تقييمات + شارة موثّق + إبلاغ + ترويج مدفوع.
6. توسيع للمنتجات + دمج المتاجر الكاملة + اشتراكات.
7. مدفوعات (CMI) + Escrow → عمولة لكل بيع + حلّ النزاعات.

**المسار ج — إكمال الموجود (كسب سريع):**
8. وصل الميزات الخلفية الجاهزة بواجهة (export/QR/backups/جمع التعليقات).
9. ربط i18n فعلياً + تقسيم `ProductsPage` + سلة خدمة متعددة.

> **التوصية:** أنجِز **المسار أ** (تصليب) ثم ابدأ **المسار ب3–ب4** (أصغر MVP حقيقي للـ Marketplace). تجنّب بناء كل شيء دفعة واحدة.
